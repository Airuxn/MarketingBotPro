Part 1: System Overview & Architecture

1.1 What is MarketingBot Pro?

MarketingBot Pro is an AI-powered marketing automation platform built with Next.js 14, TypeScript, and Google Gemini AI. It helps businesses create, schedule, and publish social media content and email campaigns while learning from user preferences to improve over time.

1.2 Technology Stack

Frontend:
  • Next.js 14 (App Router) - React framework
  • TypeScript - Type safety
  • Tailwind CSS - Styling
  • Zustand - State management with localStorage persistence
  • React Hot Toast - Notifications
  • Recharts - Analytics charts
AI & APIs:
  • Google Gemini (2.5 Flash, 2.0 Flash, 1.5 Flash, Pro) - Content generation
  • Facebook Graph API - Social media integration
  • Twitter API v2 - Social media integration
  • LinkedIn API v2 - Social media integration
  • Instagram Graph API - Social media integration

1.5 Data Storage System

Storage Location: localStorage

All application data is stored in the browser's localStorage under the key marketing-bot-storage. This includes:

  • Posts: Last 50 posts (drafts, scheduled, posted) - optimized for free-tier
  • Leads: Last 50 leads - optimized for free-tier
  • Contact Lists: Up to 20 lists with contacts - optimized for storage
  • Email Campaigns: Last 30 campaigns - optimized for free-tier
  • Settings: All user settings including:
    • Gemini API key
    • Business information
    • Connected social accounts (tokens stored securely)
    • Brand images (up to 20 images, ~150KB each = ~3MB max) - optimized for localStorage
    • Content Preferences:
      • Accepted content (last 30) - optimized for free-tier
      • Edits (last 35) - optimized for free-tier, enough for weighted voting
      • Scanned posts (last 35, newest 14 keep images) - optimized for free-tier APIs
      • learnedStyle - The aggregated AI preferences (this is what AI uses!) - no limit, always preserved
  • Total Storage: ~5.0MB per customer (fits within 5MB localStorage limit)
  • For 20 Customers: ~100MB total, distributed across 20 browsers (no server storage needed)

Automatic Backup System

How it works:
  • Every time data is saved to localStorage, a debounced backup timer starts (30 seconds)
  • After 30 seconds of no changes, an automatic backup is created
  • Last 5 automatic backups are stored in localStorage under marketing-bot-auto-backups
  • Users can also manually export/import JSON backup files
  • Storage quota management: If localStorage is full, the app automatically cleans up old data (keeps newest, removes oldest)

1.6 State Management (Zustand)

The entire application state is managed by Zustand, a lightweight state management library. The store automatically persists to localStorage using the persist middleware.

Part 2: AI Learning System - How & When AI Learns

2.1 Understanding Rule-Based vs AI Analysis

Rule-Based Analysis (No AI, Always Available)

What it is: Traditional programming using predefined rules, patterns, and logic (NOT AI/ML).

Examples:

  • Regex patterns: /#\w+/g to find hashtags
  • Keyword matching: if content contains "excited" → add "enthusiastic" tone
  • Word counting: count words to determine length (short/medium/long)
  • Statistical calculations: average, min, max, most common patterns

Characteristics:

  • ✅ Fast - instant results
  • ✅ Always available - works offline
  • ✅ Free - no API costs
  • ✅ No quota limits

Used for: Scanning posts, accepting content, analyzing edits (fallback), aggregating preferences

AI Analysis (Gemini API - Requires API Key)

What it is: Machine learning models that understand context and meaning.

Characteristics:

  • ✅ Understands WHY changes were made (not just what changed)
  • ✅ Reads FULL content to understand complete context
  • ✅ Provides deeper insights about user preferences
  • ❌ Requires API key (from Settings)
  • ❌ Has costs/quota limits
  • ❌ Needs internet connection

Used for: Analyzing edits (when API key available) - understands WHY you made changes

2.2 When Learning Happens - Complete Timeline

LEARNING TIMELINE (Complete Flow): 1. CONNECT SOCIAL ACCOUNT └─> Auto-scan triggered (Content page loads) └─> scanTwitterAccount() / scanFacebookAccount() / etc. ├─> analyzeContent() [RULE-BASED - always runs] │ └─> styleAnalysis created (rule-based baseline) └─> analyzeContentWithAI() [AI ANALYSIS if API key available - primary method] └─> aiPreferences created (AI-based, deeper insights) └─> Scanned post saved with both styleAnalysis (rule-based) and aiPreferences (AI if available) └─> combineAllLearningSources() called IMMEDIATELY ├─> Uses AI preferences if available (prioritizes AI) └─> Falls back to rule-based analysis (learnFromScannedPosts) if no AI └─> learnedStyle updated └─> Saved to localStorage ✅ LEARNING COMPLETE (Scanned posts have HIGHEST priority, AI or rule-based) 2. GENERATE CONTENT └─> User enters prompt └─> generateContent() called (ai.ts) └─> generateLearningPrompt() called (content-learner.ts) └─> Reads learnedStyle from store (ALREADY LEARNED - no new learning here!) └─> Adds learned preferences to AI prompt └─> AI generates content matching your style ✅ CONTENT USES LEARNED PREFERENCES (no learning happens during generation) 3. EDIT GENERATED CONTENT └─> User edits content in preview └─> User clicks "Save" or accepts edited content └─> trackContentEdit() called └─> analyzeEdit() [RULE-BASED - instant] └─> analyzeEditWithAI() [AI - if API key available] └─> AI reads FULL original and edited content └─> Understands WHY changes were made └─> Stores aiPreferences in edit object └─> Edit saved to settings.contentPreferences.edits └─> aggregatePreferencesFromEdits() [RULE-BASED - weighted voting] └─> combineAllLearningSources() called IMMEDIATELY └─> learnedStyle updated └─> Saved to localStorage ✅ LEARNING COMPLETE (Edits have MEDIUM priority) 4. ACCEPT GENERATED CONTENT └─> User clicks "Accept" └─> trackAcceptedContent() called ├─> analyzeContentWithAI() [AI ANALYSIS if API key available - primary method] │ └─> aiPreferences created (AI-based, deeper insights) ├─> analyzeContent() [RULE-BASED fallback - always runs] │ └─> ruleBasedPreferences created (rule-based baseline) └─> Content saved with both aiPreferences (AI if available) and ruleBasedPreferences (always) └─> combineAllLearningSources() called IMMEDIATELY ├─> Uses AI preferences if available (prioritizes AI) └─> Falls back to rule-based (learnFromAcceptedContent) if no AI └─> learnedStyle updated └─> Saved to localStorage ✅ LEARNING COMPLETE (Accepted content has LOWER priority, AI or rule-based) 5. REJECT GENERATED CONTENT └─> REMOVED: Rejected content tracking is unnecessary because content with offensive words cannot be created in the first place due to filtering

2.3 Priority Order: How Different Sources Are Combined

Learning Priority (Highest to Lowest):
  1. Scanned Posts (Highest Priority) - Your actual posted content on social media
    • AI analysis if API key available (primary method) - provides deeper insights from your actual content
    • Rule-based fallback if no API key (fast, free, effective)
    • These represent your real style that's already working
    • Primary source for new users who connect accounts
  2. Edits (Medium Priority) - You actively changed things!
    • AI analysis if API key available (primary method) - understands WHY you changed (not just what changed)
    • Rule-based fallback if no API key
    • Uses weighted voting (all edits contribute, recent ones have more weight)
  3. Accepted Content (Lower Priority) - You accepted as-is
    • AI analysis if API key available (primary method) - extracts style preferences from approved content
    • Rule-based fallback if no API key
    • Shows what you approve without changes
  4. Rejected Content - REMOVED: Content with offensive words cannot be created in the first place due to filtering, so rejected content tracking is unnecessary

2.4 How Aggregation Works (Preventing Over-Dominance)

Edits: Weighted Voting System

When you have multiple edits, the system uses weighted voting to aggregate preferences. More recent edits have higher weight, but ALL edits contribute:

Example with 5 edits: - Most recent edit: weight = 5 (33% influence) - 2nd most recent: weight = 4 (27% influence) - 3rd most recent: weight = 3 (20% influence) - 4th most recent: weight = 2 (13% influence) - Oldest edit: weight = 1 (7% influence) Total: All 5 edits contribute 100% Key Points: ✅ Most recent edit has MORE influence (reflects current preferences) ✅ But ALL edits contribute (not just the latest) ✅ Older edits still matter (7-27% each) ✅ System uses VOTING - most common pattern across all edits wins ✅ Thresholds prevent outliers (e.g., tones need 20%+ votes to be included)

How Final Combination Works

Final Merge Priority (AI Preferences Prioritized, Rule-Based Fallback): 1. Scanned posts style → HIGHEST PRIORITY (AI or rule-based) - Uses AI preferences if available (prioritizes AI insights) - Falls back to rule-based if no AI - If scanned posts have "enthusiastic" tone → Use "enthusiastic" 2. Edits style → MEDIUM PRIORITY (AI or rule-based) - Uses AI preferences if available (understands WHY changes were made) - Falls back to rule-based if no AI - FILLS GAPS if scanned doesn't have that preference - If scanned posts don't have tone preference, use edits tone 3. Accepted content → LOWER PRIORITY (AI or rule-based) - Uses AI preferences if available (extracts style from approved content) - Falls back to rule-based if no AI - FILLS REMAINING GAPS - Only used if scanned and edits don't have that preference Example: - Scanned posts (AI): "enthusiastic" tone, "medium" length - Edits (AI): "professional" tone, "short" length - Accepted (rule-based): "casual" tone, "long" length Result: "enthusiastic" tone (from scanned - AI), "medium" length (from scanned - AI) Edits and accepted only used if scanned doesn't have that preference AI preferences always override rule-based preferences when both available

2.5 When AI is Used vs When Rule-Based is Used

Action Analysis Method AI Calls When It Happens
Scan Social Posts AI (Primary if API key)
Rule-Based (Fallback)		 1 API call per scanned post
(if API key available)		 When you connect account or on content page load
Accept Generated Content AI (Primary if API key)
Rule-Based (Fallback)		 1 API call per acceptance
(if API key available)		 When you click "Accept" on generated content
Edit Generated Content AI (Primary if API key)
Rule-Based (Fallback)		 1 API call per edit
(if API key available)		 When you edit content and save it
Aggregate Preferences Rule-Based 0 API calls Immediately after accept/edit/scan (uses stored AI results, prioritizes AI preferences)
Generate Content AI (Gemini) 1 API call per generation When you click "Generate Content"

Key Insight: AI Analysis Happens During Accept/Edit/Scan, NOT During Aggregation!

When you accept/edit/scan content, the system immediately analyzes and aggregates preferences. However, aggregation itself is rule-based (weighted voting, priority merging). It uses:

  • For edits: Stored AI analysis results (edit.aiPreferences) - already analyzed during edit, AI preferences prioritized over rule-based
  • For scanned posts: Stored AI preferences (post.aiPreferences) if available, or rule-based analysis (post.styleAnalysis) - AI preferences prioritized
  • For accepted content: Stored AI preferences (accepted.aiPreferences) if available, or rule-based analysis - AI preferences prioritized

Result: Only 1 AI call per edit (for analysis). Aggregation uses stored results, so there's no additional AI cost for combining preferences.

2.6 How learnedStyle is Created and Stored

The learnedStyle Object (What AI Uses During Generation): { tone?: string[] // e.g., ["enthusiastic", "personal"] length?: "short" | "medium" | "long" // Preferred content length hashtagUsage?: "none" | "minimal" | "moderate" | "heavy" emojiUsage?: "none" | "minimal" | "moderate" ctaStyle?: string[] // e.g., ["learn more", "get started"] structure?: string[] // e.g., ["question-based", "benefit-focused"] } Storage Location: settings.contentPreferences.learnedStyle How It's Created: 1. Individual Analysis (happens when you accept/edit/scan): - Edits: AI analysis (if API key) → stores edit.aiPreferences - Scanned Posts: Rule-based analysis → stores styleAnalysis - Accepted Content: Rule-based analysis → stores preferences 2. Aggregation (RULE-BASED - no AI): - For Edits: Uses stored aiPreferences + weighted voting (rule-based) - For Scanned Posts: Uses stored styleAnalysis + statistical aggregation - For Accepted Content: Frequency analysis (most common patterns) 3. Final Combination (RULE-BASED merging): - Priority: scanned > edits > accepted - Combines arrays (tones, CTAs, structure) using deduplication - Simple logic: prefer scanned, then edits, then accepted 4. Immediate Storage: - Updates learnedStyle IMMEDIATELY after accept/edit/scan - Saved to localStorage with the rest of settings - Available for next content generation immediately

3.4 Image Storage Details

Image Storage Strategy:

  • From Scanned Posts: Images stored as URLs (original social media URLs)
    • ✅ Saves storage space (URLs are small strings, not full images)
    • ✅ Images load directly from social media servers
    • ⚠️ Risk: If original post is deleted, image URL might break
  • From Uploads: Images stored as base64 strings
    • ✅ Self-contained (no external dependencies)
    • ✅ Works offline
    • ⚠️ Uses more storage space (~100-200KB per image)
    • ⚠️ localStorage limit: ~5-10MB total

Storage Limits & Cleanup:

  • Brand Images: Last 20 images kept total (~150KB each = ~3MB max) - optimized for localStorage
  • Scanned Posts: Last 35 posts kept, images only for newest 14 - optimized for free-tier APIs (Twitter: 1 req/15min)
  • Automatic Cleanup: When localStorage is full, oldest images removed first
  • Storage Monitoring: App detects quota exceeded and automatically cleans up

4.16 Store Persistence & Hydration

How Store Persistence Works:

  • Storage: Zustand store uses persist middleware
  • Target: localStorage with key marketing-bot-storage
  • Hydration: Store configured with skipHydration: true
    • Prevents SSR mismatches (Next.js server-side rendering)
    • Manual rehydration on client-side using useStoreHydrated() hook
    • Components use NoSSR wrapper for hydration-safe rendering
  • Automatic Backup:
    • Debounced backup creation (30 seconds after any change)
    • Last 5 automatic backups stored in localStorage
    • Backup key: marketing-bot-auto-backups
  • Storage Quota Management:
    • Automatic cleanup when localStorage is full
    • Removes oldest data first (keeps newest)
    • Smart cleanup: Removes images from older scanned posts, limits arrays to safe sizes
    • User-friendly notifications when cleanup happens
